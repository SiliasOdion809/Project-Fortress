## Incident Title

Migration of CI/CD Secret Management to AWS Secrets Manager as the Single Source of Truth

# Incident Summary

During implementation of the Project Fortress CI/CD security enhancements, a review of the deployment pipeline revealed that database credentials were still being retrieved from Terraform outputs during workflow execution.

Although AWS Secrets Manager had already been implemented, the deployment pipeline continued exposing database passwords through Terraform outputs, resulting in two independent sources of truth for sensitive credentials.

To improve security and align the deployment pipeline with modern DevSecOps practices, the workflow was redesigned to retrieve credentials directly from AWS Secrets Manager using GitHub OIDC authentication.

---

# Background

Project Fortress already included:

- AWS KMS
- AWS Secrets Manager
- GitHub OIDC Authentication
- IAM Role for GitHub Actions

However, the deployment workflow still relied on:

```text
terraform output mysql_password
terraform output postgres_password
```

to initialize the application databases.

This meant Terraform outputs remained responsible for exposing sensitive credentials during deployment.

---

# Impact

The deployment pipeline functioned correctly but introduced unnecessary security risks:

- Sensitive credentials were exposed through Terraform outputs.
- Two separate credential sources existed.
- Password rotation would become more difficult.
- Terraform remained responsible for distributing secrets instead of only provisioning infrastructure.

Although no credential leak occurred, the architecture violated the principle of maintaining a single source of truth for secrets.

---

# Architecture Before

```text
Terraform
      │
      ▼
Terraform Outputs
      │
      ▼
GitHub Actions
      │
      ▼
MySQL / PostgreSQL
```

---

# Investigation

The deployment workflow was reviewed.

The investigation confirmed that:

- Database passwords were exported using:

```bash
terraform output -raw mysql_password
terraform output -raw postgres_password
```

- Those values were passed between GitHub Actions jobs.
- Database initialization pods consumed those Terraform-derived credentials.

Meanwhile, Secrets Manager already contained the same credentials generated by Terraform.

This duplication created unnecessary complexity.

---

# Root Cause

Although Secrets Manager had been implemented, the deployment workflow had never been migrated away from Terraform outputs.

As a result:

- Terraform outputs remained responsible for distributing passwords.
- Secrets Manager existed but was not the operational source of truth.

This represented an architectural inconsistency rather than an infrastructure failure.

---

# Resolution

The deployment pipeline was redesigned to retrieve credentials directly from AWS Secrets Manager.

The following improvements were implemented:

- Added Secret ARN Terraform outputs.
- Passed Secret ARNs between GitHub Actions jobs.
- Added a new GitHub Actions step to retrieve secrets using:

```bash
aws secretsmanager get-secret-value
```

- Parsed credentials using `jq`.
- Populated GitHub Actions environment variables dynamically.
- Verified successful retrieval before database initialization.

GitHub Actions authenticated using GitHub OIDC without requiring long-lived AWS credentials.

---

# Architecture After

```text
Terraform
      │
      ▼
AWS Secrets Manager
      │
      ▼
GitHub OIDC
      │
      ▼
GitHub Actions
      │
      ▼
MySQL / PostgreSQL
```

---

# Validation

The updated deployment pipeline successfully completed:

- Configure AWS Credentials (OIDC)
- Read Database Secrets
- Verify Secrets Retrieval
- Configure Kubeconfig
- Initialize Catalog Database
- Initialize Orders Database

Successful execution confirmed:

- OIDC authentication
- IAM permissions
- Secrets Manager integration
- Secret retrieval
- JSON parsing
- Database connectivity

without relying on Terraform password outputs.

---

# Security Improvements

The migration introduced several security improvements:

- AWS Secrets Manager became the operational source of truth.
- GitHub Actions retrieved credentials directly from AWS.
- Sensitive passwords were no longer required during Terraform output processing.
- The deployment pipeline moved closer to the Principle of Least Privilege.
- The architecture became compatible with future password rotation.

---

# Lessons Learned

- Secrets should be retrieved from a dedicated secret management service rather than infrastructure outputs.
- Infrastructure provisioning and secret distribution should remain separate responsibilities.
- GitHub OIDC provides a secure mechanism for short-lived AWS authentication.
- Incremental migration significantly reduces deployment risk.
- Validating each migration step before removing legacy functionality minimizes operational impact.

---

# Remaining Cleanup

After validating the new architecture, the following cleanup tasks were identified:

- Remove `mysql_password` Terraform output.
- Remove `postgres_password` Terraform output.
- Remove password propagation between GitHub Actions jobs.
- Restrict IAM permissions from:

```text
secretsmanager:*
```

to only:

```text
secretsmanager:GetSecretValue
secretsmanager:DescribeSecret
```

for the required database secrets.

---

# Preventive Actions

Future infrastructure changes will follow these principles:

- Secrets Manager will remain the single source of truth.
- Terraform outputs will expose resource identifiers rather than secrets.
- IAM policies will follow the Principle of Least Privilege.
- Security architecture changes will include operational validation before legacy components are removed.

---

# Outcome

Project Fortress successfully transitioned from a Terraform output–based secret distribution model to an AWS Secrets Manager–based architecture authenticated through GitHub OIDC.

The deployment pipeline now aligns more closely with modern DevSecOps security practices while reducing credential exposure and improving maintainability.
